# Evidence report: 3.5 sandbox for code tools (+ Part 0: real-home guard, CLI data location)

Branch: `feature/agentos-2.0-phase3.5-sandbox` (off `2.0` at `e11d232`). Status: IN PROGRESS. This section was
written before the implementation (owner instruction) and is kept in sync with what was built.

## Design decisions

Where the prompt was unsound or ambiguous the safer option was chosen; those are marked **[deviation]** or
**[change]**.

### D1. Real-home guard (Part 0a)
- New `agentos/core/home_guard.py`. Active only when `AGENTOS_FORBID_REAL_HOME=1`; otherwise behaviour is unchanged.
- The real home comes from the OS account, never from `HOME`/`USERPROFILE` (the pytest conftest points those at a
  temp folder): Windows `SHGetKnownFolderPath(FOLDERID_Profile)`, POSIX `pwd.getpwuid(os.getuid()).pw_dir`.
  Tests point the guard at a fake home with `AGENTOS_GUARD_REAL_HOME`.
- Check = (1) lexical check of the absolute, normalized path (case-insensitive on Windows) BEFORE anything is
  resolved, so a forbidden path is never opened; then (2) the same check on the resolved real path (symlinks and
  junctions followed with `os.path.realpath`).
- **[deviation]** The guard resolves the profile folder but never `~/.agentos` itself (rule 13: never open
  anything in it). A `~/.agentos` that is itself a symlink elsewhere is therefore not followed (known gap).
- Refusal: `RealHomeForbidden` (RuntimeError) naming the path and `AGENTOS_FORBID_REAL_HOME`.
- Enforced in: `default_vault_path`, `default_master_key_path`, `default_token_path`, `open_file_storage`, the
  data-dir resolver, `create_app` (project, vault, key, token), the CLI root callback and project paths, and
  `main.py`'s project resolution (the default workspace `~/.agentos/workspace` is refused while the guard is on).
- The pytest conftest sets it for the whole session; `.claude/settings.json` sets it for Claude Code.

### D2. One resolver for the data location (Part 0b)
- Cause: the server (via `main.py`) uses `--project`, else the current folder if it has `agentos.config.yaml`,
  else `~/.agentos/workspace`, and Mongo iff `AGENTOS_MONGO_URI` is set; the CLI used `AGENTOS_PROJECT` or the
  current folder and chose Mongo from `AGENTOS_STORAGE`.
- New `agentos/core/locations.py`: `resolve_project_dir(arg)` = `--project`, else `AGENTOS_PROJECT` (what
  `main.py` sets for the server), else the current folder if it has `agentos.config.yaml`, else the default
  workspace. `main.py` uses it too. `open_app_storage(project)` = Mongo iff `AGENTOS_MONGO_URI` (the server's
  rule), else file storage at the project; `create_app`'s lifespan uses the same Mongo branch.
- **[change]** The server now honours `AGENTOS_MONGO_DB` like the CLI (before it was silently ignored; default
  `agentos` unchanged).
- `agentos users create-admin` prints the data location (path or Mongo database name; never the URI) before
  asking for the password.
- `create_app(project_path=None)` keeps "AGENTOS_PROJECT or cwd" (public API unchanged).

### D3. Sandbox interface (`agentos/sandbox`)
`SandboxService.run(kind, payload, files_in, limits) -> SandboxResult{exit_code, stdout, stderr, files_out,
limit_hit, duration_ms, backend, runtime_id}`; `kind` is `python` or `shell`; `runtime_id` is the image digest or
the wasm build sha256. Backend choice (admin setting): `auto` (docker, else wasm for python), `docker`, `wasm`,
`off`. No backend (or `off`, or `shell` without Docker) -> `SandboxUnavailable`, the tool call is refused with a
clear message (fail closed). There is NO code path that runs user code as a plain host subprocess.

### D4. Docker backend (strongest; the only one for shell)
- Docker CLI via `subprocess` argument lists (never a shell). The CLI is not pip-pinnable: Docker >= 24 required,
  client/server versions shown in the status.
- Image: from the admin allowlist only, referenced by digest. Default allowlist:
  `python:3.12-slim@sha256:5e2bdb1b0d542d5039cffb8181c65930093949194a65c365dfb1b0fe13a4fa5b` (OCI index digest
  read from Docker Hub on 2026-11-21). Images must contain `python3` and `sh`.
- Flags: `--network none --read-only --cap-drop ALL --security-opt no-new-privileges --user 65534:65534
  --pids-limit 64 --memory 512m --memory-swap 512m --cpus 1 --ulimit nofile=256 --tmpfs /tmp:size=16m,noexec,
  nosuid,nodev`, default seccomp (never `unconfined`), no `-v`/`--mount` of any host path, no Docker socket,
  labels `agentos.sandbox=1`, `agentos.run=<run id>`.
- **[deviation]** The workspace is a tmpfs `/workspace` (size 50 MB, uid 65534, mode 700) instead of a bind of a
  fresh host temp dir: no host path is mounted at all, and the 50 MB cap is a kernel limit (a bind mount lets 30 s
  of writes fill the host disk and could only be checked afterwards). Files go in and out as a tar stream on the
  container's stdin/stdout, handled by an AgentOS-written bootstrap (`python3 -I -S -c ...`) running as PID 1:
  unpack input -> run the user code as a child with stdout/stderr to tmpfs files -> print one framed JSON result
  (exit code, stdout/stderr capped to 100 KB each, base64 tar of `/workspace`). The result is untrusted data like
  any tool output; the limits that matter are enforced by the host (timer -> `docker kill`, `docker inspect`
  `OOMKilled`, capped read of the container's stdout).
- Lifecycle: `docker create` -> `docker start -ai` -> `docker inspect` -> `docker rm -f` in `finally` (always
  removed); leftovers labelled `agentos.sandbox` are removed at server start.

### D5. wasm backend (Python only; no Docker needed; Windows works)
- `wasmtime==50.0.1` (optional extra `sandbox-wasm`).
- CPython WASI build pinned by URL + sha256 (VMware Labs webassembly-language-runtimes, single file with the
  standard library embedded):
  `https://github.com/vmware-labs/webassembly-language-runtimes/releases/download/python%2F3.12.0%2B20231211-040d5a6/python-3.12.0.wasm`,
  26,267,204 bytes, sha256 `e5dc5a398b07b54ea8fdb503bf68fb583d533f10ec3f930963e02b9505f7a763` (matches the
  release's published `.sha256sum`).
- Download only by an explicit admin action (`agentos sandbox install-wasm` or the Settings button, audited), never
  at run time. The hash is verified before the file is moved into `<data dir>/sandbox/wasm/` (mismatch: refused,
  download deleted) and again whenever the build is loaded. Data dir: `AGENTOS_DATA_DIR`, else `~/.agentos/data`
  (through the real-home guard). The compiled module is cached next to it (keyed by build hash + wasmtime version).
- Isolation: run in a child process that only runs wasmtime (`python -I -m agentos.sandbox._wasm_child`, minimal
  environment, killed on timeout: no orphans; a wasmtime crash cannot take the server down). WASI preview1 has no
  sockets (no network). Only the per-call workspace is preopened as `/workspace`; stdout/stderr files live
  OUTSIDE it; guest environment empty; fixed argv. Memory: store limit (512 MB). CPU/time: epoch interruption at
  the time limit, process kill as a backstop. A watcher stops the guest when stdout/stderr or the workspace exceed
  their caps (small overshoot possible, then truncated / refused).
- Not applicable: pids (WASI has no fork/processes) and CPU count (one thread).

### D6. Limits (admin settings, audited)
Defaults: 30 s, 512 MB, 1 CPU, 64 processes, 100 KB stdout and 100 KB stderr, 50 MB workspace, 20 sandbox calls per
run. Stored like the usage settings (file `.agentos/state/sandbox.json`; Mongo `sandbox_settings`) together with the
backend mode, the image allowlist and the default image; every change is audited (`sandbox.settings.update`, old and
new values). The per-run call limit is a new 3.2 run-limit kind (`RunLimits.max_sandbox_calls`, per-flow values may
only lower it); exceeding it emits `run_limit_exceeded {limit: "sandbox_calls"}` and trips the run guard (the run
fails like on the other run limits). `limit_hit` is one of `timeout`, `memory`, `pids`, `output`, `workspace` or
null.

### D7. Tools and how they reach the sandbox
- New NodeSpecs + `AGENT_TOOL_TYPES`: `python_exec {code, files?}` (docker or wasm), `shell_exec {command, files?}`
  (docker only), `file_read {path}`, `file_write {path, content}`. They go through the shared `ToolCatalog` and
  the `AgentOSToolProxy` like every other agent tool (CrewAI never calls them directly).
- Side-effect class `none` (no network, no host files), no sink rules: the code MAY be untrusted (LLM-written).
- Per-run workspace on the host (`<data dir>/sandbox/runs/<run id>/`): it is the input of every exec and is
  replaced by the validated output; `file_*` operate on it directly (no code runs); deleted when the run ends
  (plus a start-up sweep of workspaces older than 24 h). `files` arguments are `{relative path: text}` written into
  it first.
- One path rule for `file_*`, `files` and copy-out: relative only; refuses absolute paths, `..`, drive letters
  (also `C:x`), UNC and `\\?\` forms, `:` (Windows alternate data streams), NUL/control characters, Windows
  reserved names (CON, NUL, ...), over 255 characters; backslashes are separators. Copy-out refuses symlinks, hard
  links (`st_nlink > 1`; tar link members), devices and fifos; caps 10 MB per file, 50 MB in total.
- Labels: every output (stdout, stderr, `file_read` content, files) is UNTRUSTED with confidentiality = join of
  the agent context and the workspace label. The workspace label is the join of every label written into it in
  this run, rebuilt from the run's `sandbox_exec`/`file_write` events (so a later agent node reading the file
  inherits it). Secret in -> secret out; the existing proxy rules then block sending it to an external sink.
- Nothing from the host is passed in: no environment variables (container and guest environments are empty), no
  vault, no provider keys, no `AGENTOS_*` values.
- Agent tool picker: `/api/v2/agents/tool-options` offers `python_exec`/`file_*` only when a backend supporting them
  is available and `shell_exec` only with Docker. Saving an agent with them stays allowed; the run refuses if no
  backend is available at that time (fail closed).

### D8. Events, audit, UI
- Event `sandbox_exec`: agent node, tool, backend, runtime id (image digest or wasm hash), duration, exit code,
  limit hit, stdout/stderr sizes and capped text, files out (names, sizes), label. The code itself is in
  `tool_called.args` and is shown as an untrusted value like any tool argument.
- Audit: `sandbox.settings.update`, `sandbox.wasm.install`, `sandbox.test`.
- API: `GET /api/v2/sandbox/status` (read), `GET|PUT /api/v2/sandbox/settings`, `POST /api/v2/sandbox/test`
  (runs `print(6*7)`), `POST /api/v2/sandbox/wasm/install` (admin).
- UI: Settings -> Sandbox (status, versions, limits, image allowlist, Test sandbox, Install wasm runtime); the run
  panel shows exit code, limit hit, stdout/stderr as plain text marked UNTRUSTED, and files out.

### D9. Tests and labels
Real Docker tests are **LIVE (docker)**; real wasmtime tests are **LIVE (wasm)**; the model is always MOCK
(scripted). A new CI job `sandbox-docker` (ubuntu) sets `AGENTOS_REQUIRE_DOCKER=1` so Docker tests FAIL there
instead of skipping; locally they skip when Docker is not running. `python-ci` installs the wasm extra and the
pinned build (cached) with `AGENTOS_REQUIRE_WASM=1`, so the wasm tests and use case 12 really run in CI.
