# Evidence report: 4.2 test cases for flows

Branch `feature/agentos-2.0-phase4.2-flow-tests` off `2.0` at 5d845d0 (includes 4.1b). Status: in progress.

## Design decisions

**D1 Layout (ports and adapters).** New domain package `agentos/flowtests/` (no FastAPI/Mongo imports):
`models.py` (TestCase, Expectation, Fixture, CaseResult, SuiteRun, GateSettings), `expectations.py`
(evaluators + readable diffs), `fixtures.py` (fixture network + fixture MCP manager + recording sinks),
`models_choice.py` (MOCK scripted model, router, chosen model), `runner.py` (run_case / run_suite),
`generate.py` (from run, from review export, security tests), `compare.py` (model comparison, regression),
`judge.py`, `store.py`. Server: `agentos_server/routes_v2/flow_tests.py`. CLI: `agentos test` in
`agentos/cli/main.py`.

**D2 Storage (file + Mongo).** Reuse the 3.3/3.6a document-store pattern: `FileDocs`
(`agentos/notify/store.py`) -> `<project>/.agentos/state/flow_test_cases.json`, `flow_test_runs.json`,
`flow_test_settings.json`; `MongoDocs` (`agentos/storage/mongo/notify.py`) -> collections `flow_test_cases`,
`flow_test_runs`, `flow_test_settings`. `flowtests_store_for(storage)` picks by `storage.backend`, like
`review_store_for`. Suite history: the last 50 suite runs per flow are kept. Mongo tests are marked like the
existing mongo-live ones (skip without `AGENTOS_MONGO_URI`, run in the mongo-live CI job).

**D3 Test case.** `id, flow_id, name, tags[], input (trigger payload), fixtures[], mock_responses{node_id: text}
(MOCK script), approvals[] (decisions applied in order when the run waits, default: none -> run stays waiting),
expectations[], source ("manual"|"run"|"review"|"security"), attack (security cases only), created_by/at`.
Fixture: `{kind: http|mcp, method?, url? (exact, or prefix with trailing *), tool?, status, body, recorded:
bool}`. Expectation kinds (each a typed model with `kind`):
- `status`: equals succeeded | waiting_for_approval | failed (maps RunStatus `waiting`).
- `output`: node, field path (dotted or `$.a.b` JSON path), op equals | contains | regex | json_path_equals, value.
- `extraction`: node (quarantined_extraction or validator), field, equals; the value is checked at save against
  the node's allowed values (enum/bool/allowlist), refused (400) otherwise.
- `sink`: target `send_email` | `send_slack` | `http_request` | `mcp:<tool>` (optional node), op called |
  not_called | count (n) | called_with (arg `to`/`channel`/`host` equals X, normalised like 4.1 `email_dests`).
- `security`: op blocked (a tool_call_blocked/rejected event or a security error, optional node) |
  publish_refused (StaticFlowAnalyzer on the tested version) | no_external_send (no destination outside
  `policy.internal_domains` for email, outside the configured Slack channels/internal for Slack, outside
  `http_allowlist` for HTTP).
- `approval_reached`: optional node.
- `limits`: max_cost_usd, max_duration_ms, max_model_calls.
- `judge`: rubric + fixed reason list -> D9; marked `nondeterministic: true`.
Every failure produces `{expectation, expected, actual, message}`; the UI and JUnit show "expected X, got Y".

**D4 Running: never a real side effect (most important rule).** A case runs the real `FlowEngine` (same as a
normal run, so all labels, sink rules, the proxy and run limits apply) with `trigger="test"` and run id
`test_<hex>` in the real storage, so the run opens in the run panel. Transports (built per case, never the app's):
- `send_email`, `send_slack`: `MockTransport` recorders (always, also with live tools).
- `http_request`, `fetch_url`: the real `HttpRequestTransport` (real SSRF guard and allowlist) with a fake
  resolver (public test IP) and a fixture sender; no matching fixture -> the miss is recorded and the case
  FAILS with `no fixture for http_request GET https://host/path` (fetch_url turns errors into text, so misses are
  checked after the run, not only via exceptions).
- MCP tools: a `FixtureMCPManager` with the `call_tool` interface used by `agentos/flows/proxy.py`; fixture by
  tool name, else miss -> `no fixture for mcp:<tool>`.
- Admin-only **live tools** (default off, audited `flow_tests.live_tools`): `http_request`/`fetch_url` GET may use
  the real resolver + sender when no fixture exists; every non-GET still needs a fixture; email/Slack stay fake.
- A tripwire test (reusing `benchmarks/awib/tripwire.install`) runs a suite touching email, Slack, HTTP and
  fetch_url and asserts no SMTP, httpx network transport, net_guard sender or DNS call happened.

**D5 Targets and models.** Target: `draft` | `published` (latest) | `version N`. Model:
- `mock` (default, free): a scripted `BaseLLM` (pattern of `agentos/redteam/adversary.py`): agent nodes get
  `Final Answer: <mock_responses[node] or default>`, llm nodes the text, extraction nodes the scripted JSON or
  `extraction.mock_output`. Security cases use the 4.1 adversarial model for their attack.
- `router`: `custom_llm=None` (normal fallback chain, through RunGuard budgets/run limits).
- `provider/model` (1..4 chosen): the isolated flow copy sets `config.model` on every llm/agent/extraction
  node; the model must be served by an enabled provider (same check as `_check_node_models`).
Real calls go through the router, count against budgets and run limits, and are tagged as test usage: a small
engine option `usage_source="test"` puts `source: "test"` on llm_call records and the ledger row key gets a
`|test` suffix (existing keys unchanged, budgets still count them; the usage API returns `source`).

**D6 Results and history.** CaseResult: `case_id, name, status pass|fail|error, failures[], error, run_id,
cost_usd, duration_ms, model_calls, models_used[], nondeterministic`. SuiteRun: `id, flow_id, target, version,
model, tags, started_at, counts, results[], regression, comparison_id`. Stored with history (D2).

**D7 Model comparison.** 2-4 model specs -> the suite runs once per model (sequentially) -> table rows: model,
pass rate, total cost, median latency (median `latency_ms` of llm_call events; case duration for MOCK), failed
cases. Each per-model run is stored as a SuiteRun with a shared `comparison_id`.

**D8 Regression.** Each suite run is compared with the previous suite run of the same flow: newly failing
(pass -> fail/error), newly passing, still failing, plus new/removed cases. Stored on the SuiteRun, shown at the
top of the results.

**D9 Judge.** Built on 2.5b quarantined extraction: an isolated one-node flow (trigger -> quarantined_extraction
with fields `verdict: enum[pass, fail]`, `reason: enum[<fixed list>]`, rubric in the instructions, input = the
chosen node output) run through `FlowEngine` with the same model choice (router -> budgets/usage). Output is only
pass/fail plus one reason from the fixed list. Clearly marked non-deterministic in results, UI and JUnit; in MOCK
it returns the scripted verdict (default pass).

**D10 Publish gate** (per flow, set by builder/admin, audited `flow_tests.gate`, default off). Modes `warn` |
`block`, plus the gate model (default `mock`). In `publish_flow` the structural, model and static security checks
run first, as today; then, if the gate is on, the suite runs against the draft. `block`: any failing case (or no
cases at all: fail closed) -> 400 `Publish refused: tests failed` + audit `flow.publish` refused
`reason: tests_failed` with counts. `warn`: publish goes ahead; the response carries a response-only
`test_gate` field (like `published_version`) with counts and failing case names, shown as a warning.

**D11 Creating cases.**
- *From a run* (`POST .../tests/from-run`, returns a draft, nothing saved): input from `flow_started`, fixtures
  from http_request node outputs (status/body); fetch_url and MCP events hold metadata only (by design since
  3.3/2.5a), so their fixtures are created with the URL/tool and an empty body marked `recorded: false` ("fill in
  the response"); mock_responses from agent/llm node outputs (exact MOCK replay); suggested expectations: final
  status, each sink called/not called with its recipients, approval reached, extraction fields, key outputs.
- *By hand* in the editor.
- *From the 3.6a review export* (`ReviewStore.export_items`): each reviewed item of this flow with a
  `corrected_output` becomes a case whose expectation is `output equals corrected_output` on that node (else
  the reviewed output if verdict good); input from the item.
- *Security tests* (`POST .../tests/security`): `agentos.redteam.attacks.generate(flow)` (MCP families skipped
  as in 4.1), input via `redteam.runner.inject`, adversarial MOCK model, expectations: no send to the attack's
  targets, `security.no_external_send`, tag `security`.
- **SECRET**: values whose run label confidentiality is `secret` (and review-export `[SECRET redacted]`) are
  never stored as expected values or fixture bodies: replaced with a placeholder and the expectation dropped with a
  note, unless an admin sets `include_secret_values` (403 for non-admins; audited `flow_tests.secret_values`).

**D12 API + permissions** (all added to `permissions_table.py`; viewer read, builder/admin build; admin-only
options are checked in the handler with `allows(role, "admin")`):
`GET/POST /flows/{flow_id}/tests` (read/build), `GET/PUT/DELETE /flows/{flow_id}/tests/{case_id}`,
`POST .../tests/from-run`, `.../tests/from-review`, `.../tests/security` (build), `POST .../tests/run`,
`.../tests/compare` (build), `GET .../tests/runs`, `.../tests/runs/{suite_run_id}` (read),
`GET/PUT .../tests/settings` (read/build), `GET /flow-tests/summary` (read; flow card pass rates).
Audit: `flow_tests.run` (counts only), `flow_tests.gate`, `flow_tests.live_tools`, `flow_tests.secret_values`,
`flow_tests.case` save/delete (ids and counts only, never inputs or expected values).

**D13 CLI.** `agentos test <flow_id> [--version N] [--draft] [--model mock|router|provider/model]
[--tags security] [--junit out.xml] [--project DIR]`: `resolve_project_dir` + `open_app_storage` (same
resolution as the server) and the same SecurityPolicy loaders as `create_app` (moved to a shared helper only if
they cannot be imported). Exit 0 only if all cases pass; 1 if any fails/errors; 2 setup error (flow/version not
found, no cases, unknown model). JUnit: one testcase per case, failures with the diff text.

**D14 UI.** Flow editor "Tests" tab/panel (`ui/src/flow/TestsPanel.tsx`, `ui/src/api/flowTests.ts`): list
(name, tags, last result), editor with an expectation builder (kind select + fields), Run all (target + model),
results (regression summary on top, per-case diffs, run link opening `?run=`), model comparison table, gate
settings. RunPanel: "Save as test case" -> from-run draft opened in the editor. Overview/Flows card: last pass
rate when tests exist. New Playwright spec `ui/e2e/builder-tests.spec.ts` (builder config, MOCK).

**D15 Use case 15** `examples/usecases/15-flow-tests/`: suite for the 07 support desk (urgent -> approval reached
and only oncall@corp.local; normal -> support queue only; injection -> no send to the attacker; plus generated
security tests), `run.py` (MOCK), `tests/ci/test_usecase_15.py`.

**D16 Not in scope / labelled.** Judge and router/provider runs are not run LIVE in CI (MOCK only; LIVE needs
keys). Live tools are tested with a fake sender only. Fixture bodies for fetch_url/MCP cannot be recorded from a
run (metadata-only events, by design).
