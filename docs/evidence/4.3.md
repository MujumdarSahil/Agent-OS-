# Evidence report: 4.3 versions, environments, promotion, rollback and version diffs

Branch `feature/agentos-2.0-phase4.3-environments` off `2.0` at df20e19 (includes 4.2). Status: in progress.
All results are MOCK unless labelled otherwise.

## Design decisions

Written before implementation; the code implements exactly these. Any later deviation is listed under
"Deviations from the design" with its reason.

**D1 Storage.** New port `DeploymentRepository` (`agentos/storage/ports.py`), field `Storage.deployments`.
- `DeploymentRecord {flow_id, environment: "staging"|"production", version, deployed_by, deployed_at, note,
  action: migrate|publish|promote|rollback, previous_version}`; `EnvironmentSettings {flow_id, auto_deploy_staging,
  auto_deploy_production, promote_test_gate: off|warn|block, second_person: bool, legacy: bool}`.
- Methods: `get(flow_id, env)`, `current(flow_id) -> {env: rec}`, `set(flow_id, env, version, expected_version, ...)`
  (compare-and-set; raises `DeploymentConflict` when the current version != expected), `history(flow_id)`,
  `get_settings/put_settings`, global `get_staging_channels/put_staging_channels`.
- File: `<project>/.agentos/flows/<flow_id>/environments.json` (current + history), written with
  `atomic_write_text` under an exclusive lock file (`O_CREAT|O_EXCL`, short retry, stale-lock timeout) plus an
  in-process lock, so read-check-write is atomic across threads and processes. Global settings in
  `.agentos/state/environments.json`.
- Mongo: `flow_deployments` (`_id = flow:env`; CAS = `find_one_and_update({_id, version: expected})`, or
  `insert_one` when expected is None -> DuplicateKey = conflict), `flow_deployment_history`, `flow_env_settings`.
  Tested in the mongo-live job (new `test_environments_mongo_live.py`, same skip rule as 4.2).
- Versions are never deleted (stricter than asked; today there is no version delete). New: archive a version
  (`archived_versions` list in the per-flow environments doc); an archived version cannot be promoted/rolled back
  to or chosen for new runs, but stays readable and runs in progress keep it.

**D2 Migration / "existed before 4.3".** A flow is legacy if it has no `EnvironmentSettings` record.
- Startup (create_app lifespan): every existing flow without settings -> settings `{legacy: true,
  auto_deploy_production: true, auto_deploy_staging: true}` and, if it has published versions,
  production = latest (action `migrate`, deployed_by `system:migration-4.3`); staging empty. Idempotent.
- Any server path that saves a draft / publishes a flow without settings writes NEW-flow settings
  (`auto_deploy_production: false`).
- Lazy fallback: a trigger/run resolving an environment for a flow with no settings record (data that appeared at
  repository level, e.g. a restore of a pre-4.3 backup) applies the same legacy migration first (CAS create).
  So pre-4.3 data, and existing tests that publish at repository level, keep today's behaviour.

**D3 What runs where.** One resolver `agentos/flows/environments.py::resolve_run_target(...)`.
- `WebhookRecord.environment` / `ScheduleRecord.environment` (default `"production"`; existing records load as
  production). At run START the resolver reads the environment's version; `RunRecord` gets `environment` (new) and
  `flow_version`; the queue job carries the version, so a later promote/rollback never changes a started run
  (worker loads `get_version(job.version)` as today). Environment empty -> webhook returns the same generic 404 as
  today (logged), scheduler skips the tick with a warning, nothing runs.
- Manual run `POST /flows/{id}/runs` body gains `environment: draft|staging|production` (optional) alongside
  `version`. Neither given -> production if set, else latest published (compatibility for existing API clients;
  run recorded with `environment: null`).
- Draft run: static check on the draft against the current policy first (refused if it fails); the draft is
  snapshotted into `RunRecord.flow_snapshot` (existing 4.2 field) and the worker runs the snapshot; sends are always
  SIMULATED (as staging without a mapping). The run panel labels it "draft run".

**D4 Staging is safe by default.** The worker wraps the transport registry for runs with environment `staging` or
`draft`: `send_email`/`send_slack` return `{"status": "simulated", "reason": "staging: simulated ..."}` (the run
panel's existing "simulated sends" badge shows it, plus a STAGING banner). Global admin mapping
`staging_channels {email_channel: name|null, slack_channels: [names]}`: a mapped email channel is used for staging
email (any enabled email channel, normally a test mailbox; its own recipient rules apply); send_slack to a mapped
channel is delivered; everything else stays simulated. Header-injection refusals still apply in simulation (same
code as `ChannelEmailTransport`). Production uses today's `ChannelEmailTransport`/`ChannelSlackTransport` unchanged.
Tripwire test: a staging run with a recording real transport proves zero deliveries unless mapped.

**D5 Publishing.** `POST /publish` body `{note: str (1..500, required)}`, stored on the version
(`FlowRecord.change_note`). Publish creates the version only; then auto-deploy per settings: staging (default on),
production (legacy default on, new default off). Auto-deploy to production is skipped (reported in the response
`deployments` and audited, publish still succeeds) when `second_person` is on or the promote test gate blocks.
Missing note -> 422. This is a change to the `/api/v2` publish route (v1 API untouched): listed in the report.

**D6 Promote / rollback.** Promote / rollback (`DeploymentService` in `agentos/flows/environments.py`, used by API and CLI). Checks in order,
the result audited (`flow.promote` / `flow.rollback`: who, env, from, to, version, checks):
1. version exists and is not archived;
2. static analysis re-run against the CURRENT policy and tool catalog (same code as publish: `StaticFlowAnalyzer`,
   `_resolve_subflow_summaries` moved to a shared helper, `ToolCatalog`); response shows stored vs current
   `policy_hash`; failing -> 409 refused with the violations (rollback says why the old version now fails);
3. production promote only: promote test gate off/warn/block runs the 4.2 suite against that exact version
   (`execute_suite(target="version")`); block+fail -> refused, warn -> allowed with a warning;
4. production promote only: `second_person` -> the version's `published_by` cannot promote it;
5. CAS on `expected_version` (what the client saw; omitted = value read at start) -> 409 on conflict.
Rollback = checks 1, 2, 5 to any earlier published version; UI confirmation shows the diff.

**D7 Diff.** Diff `agentos/flows/version_diff.py::version_diff(old, new, policy, catalog)`: reuses
`agentos/builder/diff.py::flow_diff` for structure and adds per-node `config`/`pinned_args` key changes
(old -> new) and `security` (shown first, items `{kind, node, detail}`): `sink_added`, `sink_removed`,
`recipient_changed` (pinned `to`/`channel`/url host, incl. agent tool pins), `approval_removed`,
`validator_loosened` / `extraction_loosened` (enum/allowlist grew, bounds widened, constrained type removed),
`new_untrusted_path` (source->sink pairs from the analyzer's label propagation: new read-only
`StaticFlowAnalyzer.untrusted_sink_paths()`), `analysis_changed` (valid/violations before vs after, both against the
current policy). API `GET /flows/{id}/diff?from=3&to=draft`. UI reuses the 4.0 `DiffView` (BuilderPreview.tsx) with
a "Security-relevant changes" block above it.

**D8 Versions list.** Versions list `GET /flows/{id}/versions/summary`: number, note, published_by, published_at, test pass rate
(latest 4.**2 suite run for that version), security check status against the current policy, environment badges,
archived, used by runs.

**D9 Permissions.** Permissions (every new route in `permissions_table.py`; environment-specific actions are separate literal paths so
the table decides by capability, deny by default):
- read: `GET versions/summary`, `GET environments`, `GET environments/history`, `GET diff`.
- build: `POST environments/staging/promote`, `POST environments/staging/rollback`,
  `PUT environments/settings/staging` (auto_deploy_staging), `POST versions/{v}/archive`, publish (unchanged).
- admin: `POST environments/production/promote|rollback`, `PUT environments/settings/production`
  (auto_deploy_production, second_person, promote_test_gate), `GET/PUT /environments/staging-channels`,
  `PUT /webhooks/{id}/environment`, `PUT /schedules/{id}/environment`. A builder may pick the environment when
  CREATING a webhook/schedule; changing it later is admin-only (the existing builder PUTs refuse a changed value).
Every settings change audited (`flow.env_settings`, `env.staging_channels`, `webhook.environment`, `schedule.environment`).

**D10 CLI.** CLI `agentos flows versions|diff|promote|rollback <flow_id>` (new `flows` typer group; storage via
`open_app_storage(resolve_project_dir(project))` and policy from admin_config, same as `agentos test`).** Actor `cli`.
Exit 0 ok, 1 refused (check failed / conflict / second-person), 2 setup error. The CLI is a local operator tool
(same trust as `agentos test`); role checks apply to the API (documented gap until per-user CLI auth).

**D11 UI.** UI: FlowEditor "Versions" panel (list + badges, pick two -> Compare, Promote, Rollback with a confirmation dialog
showing the diff, Archive); Publish dialog asks for the note (max 500, counter); Flows list shows
"prod vN / staging vM"; Run dialog environment choice (draft/staging/production/version); run panel STAGING/DRAFT
banner; Triggers page shows each webhook/schedule environment (admin can change it).** New Playwright spec
`ui/e2e/builder-environments.spec.ts` (picked up by the builder config).

operator tool, like `agentos test`); a manual run with neither version nor environment still runs the latest
published version when production is empty (API compatibility).
