# 2.5b evidence: quarantined extraction

Branch `feature/agentos-2.0-phase2.5b-extraction`, cut from `feature/agentos-2.0-phase2.5a-mcp` at `d01ecec`
(PR #45 was not merged when this started). All results are **MOCK** (scripted model, no keys, no network).

## Design decisions (written before the implementation)

### What the node is
`quarantined_extraction` reads untrusted text, asks a model to fill only strictly constrained fields,
validates every value, and outputs only the validated values. Its outputs are declassified to trusted
integrity. It's the third declassification path, after `approval` and `validator`.

### Data model (node config; `additionalProperties: false` at every level)
```
{
  "input": "text",                     # optional: the name of ONE input argument mapped by an edge (default "text")
  "fields": [                          # 1-10 entries, names unique, ^[a-z][a-z0-9_]{0,31}$
    {"name": "category",  "type": "enum",      "values": ["phishing", "spam", "legit"]},  # 2-50, unique, <=64 chars, [A-Za-z0-9 _.-]
    {"name": "needs_reply","type": "bool"},
    {"name": "count",     "type": "int_range", "min": 0, "max": 5},                       # |min|,|max| <= 10^9, min <= max
    {"name": "ticket",    "type": "pattern",   "pattern": "ticket_id"},                   # uuid | sha256 | iso_date | ticket_id
    {"name": "owner",     "type": "allowlist", "allowlist_name": "oncall"}                # a SecurityPolicy allowlist
  ],
  "on_invalid": "fail",                # "fail" (default) | "default"
  "defaults": {"category": "spam", ...},   # required for every field when on_invalid = "default"; each validated
  "model": "groq_gpt_oss_20b",         # optional; else the router's default chain
  "max_input_chars": 20000             # default 20000, 1..100000
}
```
- **No free-text type exists.** The JSON Schema is a `oneOf` per type, so a field without one of the five
  constraints doesn't validate.
- **Two layers of validation:**
  - The schema runs in `FlowDefinition`, on save and on publish.
  - A semantic check runs in the static analyzer at publish. It covers unique names, unique enum values,
    `min <= max`, that the allowlist exists in the policy, and that each default is present and passes its own
    field's constraint.
- **Input: a single upstream field, no expressions.** The prompt allows "an expression or a single upstream
  field". I support only an edge-mapped input argument. That's the safer choice: the edge on the canvas shows
  the data path, and publish and run time see exactly the same input label. An expression can read an ancestor
  that isn't connected by an edge, and then the publish-time label might not include its confidentiality.

### Label rule (one shared function, used by the static analyzer and the engine)
`extraction_output_labels(node_id, fields, inbound)` in `agentos/flows/extraction.py` gives each field:
- **integrity:** `trusted`;
- **confidentiality:** the confidentiality of the node's effective inbound label (the join of everything that
  reaches it), so extracting a category from confidential text stays confidential;
- **sources:** the inbound sources, plus the node id, plus a marker
  `declassified:quarantined_extraction:<node_id>:<field>:<type>`.

The `*` label is the join of the field labels. Expressions and templates built only from these fields are
trusted, so `{{ nodes.extract.category }}` may reach an `EXTERNAL_SEND` body argument. Because the analyzer and
the engine call the same function with the same inbound label, publish and run time give identical labels
(tested).

### Where the DESTRUCTIVE and recipient rules are enforced
Both live in `agentos/flows/rules.py`, which the static analyzer (publish) and the engine (run time) already
share. The marker in a label's sources is what they look for.
1. **Arguments** (`evaluate_sink_argument_rule`, a new check): if the sink's side effect is `DESTRUCTIVE`, the
   argument isn't pinned or approved, its label is trusted, and it carries an extraction marker, that's a
   violation. Exception: `SecurityPolicy.allow_extraction_for_destructive` is true.
2. **Control dependency** (`evaluate_control_dependency`, extended): for a `DESTRUCTIVE` sink whose deciding
   predicate is trusted only because it carries an extraction marker, that's a violation. Exceptions: the sink
   is approval-gated (an `approval` node names it in `approves.sink_node`), or the policy flag is true.
3. **Recipients** (`evaluate_sink_argument_rule`): for an `EXTERNAL_SEND` recipient argument (`to`, `cc`, `bcc`,
   `recipient`, `recipients`) that isn't pinned, any extraction marker whose field type isn't `allowlist` is a
   violation, even though the label is trusted. An enum value must never become a recipient.

`allow_extraction_for_destructive` defaults to false and is admin-only: it's read from `agentos.config.yaml`
(`security.allow_extraction_for_destructive`) or `AGENTOS_ALLOW_EXTRACTION_FOR_DESTRUCTIVE`, never from a flow.
The approval exception for arguments reuses the existing "approved argument" rule, which requires an edge
mapping from an approval node that names this sink and argument.

**Unsound part of the prompt, and the safer choice:** "a value that is trusted for another reason". A label
that joins an extraction value with a pinned or other trusted value is still steerable through the extraction
part. So I treat any extraction marker in a destructive argument or predicate as "enabled by extraction" unless
it's approved, or unless the value is pinned (pinned values never carry the marker).

### Model call path
One direct call: `AgentOSRouterLLM.call(messages, tools=None)`, built by the engine's existing `_router_llm`.
- No CrewAI, tools, function calling, memory, delegation or agent loop.
- The router makes one attempt per provider in its normal fallback chain, and nothing feeds the model's invalid
  output back to it.
- T-13 applies: secret-labelled input makes the router local-only.
- Tests (and use case 09) pass a scripted model as `custom_llm`, called the same way with `call(messages)`.
- In MOCK mode with no scripted model, a clearly labelled deterministic mock answers: the first enum value,
  `false`, `min`, a fixed example for each pattern, and the first allowlist entry.

**Prompt:** the system message is built only from the trusted config: field names, types, allowed values and
ranges. The untrusted text goes in a user message, inside a data block delimited by a random per-call nonce.
It's truncated to `max_input_chars`, and a `truncated` flag is set.

**Strict parsing:**
- Raw output over 4 KB, or anything that isn't a string, is rejected before parsing.
- One surrounding Markdown code fence is removed. That's a small leniency, documented; content inside a fence is
  parsed just as strictly.
- `json.loads` rejects duplicate keys. The result must be an object with exactly the configured keys, and no
  value may be an object or list.
- **Per type:**
  - `enum`: a string that, after `str.strip()`, equals an allowed value exactly. No case-folding or fuzzy match;
    an inner newline fails.
  - `bool`: a real JSON boolean.
  - `int_range`: a real integer, not a bool, within `[min, max]`.
  - `pattern`: a string that fully matches the built-in pattern. `iso_date` must also be a valid date; a `uuid`
    is lowercased.
  - `allowlist`: a case-insensitive match on the trimmed value; the output is the canonical entry.
- **Any failure:** `on_invalid`. Either the node fails, or the validated defaults are used.
- **Raw output:** never passed downstream and never stored in an event. Only its length and sha256 are recorded.

### Event types
- **`extraction_completed`:** `{node_id, fields: <validated values>, input_chars, truncated, provider, model,
  duration_ms, raw_len, raw_sha256}`.
- **`extraction_rejected`:** `{node_id, reason: <reason class>, field?, provider, model, input_chars,
  truncated, raw_len, raw_sha256, used_defaults}`.
- **`declassified`:** `{node_id, kind: "quarantined_extraction", fields: [names], source_sources:
  [inbound sources]}`, written after either completion or the defaults path.
- **Existing events:** `llm_call` metadata from the router (no prompt or response text), then `node_succeeded`
  or `node_failed`.

### Observed during the design
- The existing `validator` node's runtime `enum` accepts any string, and its runtime label drops the input's
  confidentiality. At first this was left out of scope; after review it was fixed in 2.5b (see "Validator
  hardening" below).

## Refinements made while implementing (each is the safer or more exact option)
1. **One inbound-label definition for both sides.** The analyzer's effective inbound label is the join of ALL
   outputs of every node with an edge into this one, but the engine's runtime inbound is only the mapped
   arguments. To keep labels identical, `extraction.shared_inbound(flow, node_id, labels_by_node, fallback)`
   computes the join of all upstream outputs on both sides. The engine calls it; it equals the analyzer's value.
   This is tested with a two-level extraction.
2. **"Approval-gated" means the approval is an ancestor.** An approval node counts only if it names the sink in
   `approves.sink_node` AND sits upstream of it (`is_approval_gated`). An approval elsewhere in the graph doesn't
   count.
3. **The DESTRUCTIVE argument rule accepts an approval-gated sink.** The analyzer conservatively labels an
   unmapped argument with the inbound label, so a DELETE behind an approval was refused because of its (absent)
   `body`. When an upstream approval releases the whole call, `evaluate_sink_argument_rule(...,
   approval_gated=True)` exempts the extraction check. The proxy (agent tool calls) doesn't pass it, so agent
   tools stay strict.
4. **Rejection messages never echo model text.** `extra_key` and `duplicate_key` don't name the key: the key is
   model output.
5. **T-13 for an injected model.** A `custom_llm` (test double or embedder) gets SECRET input only if it
   declares `is_local = True`; otherwise the result is `model_refused`. The router path uses `local_only` as
   designed.
6. **Admin allowlists are loaded by the server.** `security.allowlists` in `agentos.config.yaml` (name → list)
   didn't load before; now it does, along with `security.allow_extraction_for_destructive` or
   `AGENTOS_ALLOW_EXTRACTION_FOR_DESTRUCTIVE`. `/api/v2/node-specs` returns the allowlist NAMES (never the
   entries) and `declassifies: true` for the extraction spec only.
7. **The spec declares its input.** `input_schema` names the `text` argument, so the builder's edge drawer
   offers it.

## (d) Known gaps and things not done
- **MOCK only.** No real model was asked to extract. Whether a real model follows the format, or can be steered,
  isn't measured here; the security outcome doesn't depend on it.
- **Steering is inherent:** an attacker can choose WHICH allowed value comes out (use case 09, "steer to
  legit"). It's documented in the README Known limitations and in SPEC §2.3.
- The input is a single edge-mapped argument; there's no expression input (a design decision).
- The extraction-marker rule is conservative. Any value joined with an extraction value counts as "enabled by
  extraction" for DESTRUCTIVE sinks, including LLM output computed from extracted fields.
- Agent tool calls (proxy) don't get the approval-gated exemption for the DESTRUCTIVE argument rule. That's
  stricter, not looser.
- The router path fills `provider` and `model` from the `llm_call` record. With a custom model they read
  `custom` and the model's name.
- The validator's runtime enum and confidentiality issues (above) are not fixed in 2.5b.
- The builder's field builder isn't re-validated client-side beyond the enum chips; the server schema and
  analyzer are authoritative.

## Validator hardening (after review, same branch)

### The bypass (CRITICAL, confirmed by the reviewer, at publish AND at run time)
```
webhook_trigger -> validator {field: "to", field_type: "enum"} -> send_email (to mapped from the validator)
StaticFlowAnalyzer.verify(): is_valid=True, no violations
execute_validator_runtime(): {"to": "mallory@attacker.example"} labelled trusted
```
- **Cause:** `enum` had no values, so any string passed and was declassified. `bounded_number` had no bounds.
  `bool` accepted `"yes"`, `"1"` and numbers. The runtime label was `Label.trusted(sources={node})`: it dropped
  the input's confidentiality and its sources. The analyzer gave a different label from the runtime.

### The fix (one implementation for validator and extraction, in `agentos/flows/extraction.py`)
1. **Same types and limits as extraction.** The schema is `VALIDATOR_CONFIG_SCHEMA` and the semantic check is
   `validator_config_errors`. The validator's field is checked with the extraction `FIELD_SCHEMA`, and values
   with `validate_value`.
   - `enum`: needs `values` (2-50, same charset); exact match after trimming whitespace only.
   - `bool`: a real bool or the exact strings `"true"`/`"false"`.
   - `int_range`: needs `min` and `max`; integers only, bools rejected.
   - `pattern`: the built-in set only.
   - `allowlist`: needs `allowlist_name`; the output is the canonical entry.
   - **Old names:** `allowlist_match` = `allowlist`, `bounded_number` = `int_range` (with min and max).
   - **Refused at publish with a clear message, failing closed at run time:**
     - any other or incomplete type;
     - a key that doesn't belong to the type;
     - an allowlist that isn't configured;
     - the host-based `http_allowlist`, which can't give a canonical entry. This is a behaviour change, noted
       in the use case 06 README.

     At run time `execute_validator_runtime` raises `invalid_config`, a `validator_rejected` event is written,
     the run fails and nothing is declassified. A pre-2.5b flow still loads (the old keys are unchanged in the
     schema), so it reaches this fail-closed path instead of failing to load.
2. **One label function, `validator_output_labels`,** used by the analyzer and the engine.
   - **Sound config:** trusted, the inbound confidentiality, inbound sources + node + marker
     `declassified:validator:<node>:<field>:<type>`.
   - **Unsound config:** untrusted, same confidentiality.
   - **Inbound label:** both sides use `shared_inbound`.
   - **Events:** a `declassified` event (`kind: "validator"`) on success.
3. **The same two rules in `rules.py`, now for any declassification marker** (`declassification_markers`,
   `enabled_by_declassification`).
   - **DESTRUCTIVE:** an argument or predicate from a validator or extraction needs an upstream approval or the
     admin flag.
   - **Recipients:** only an `allowlist` type may choose one.
   - **The flag is renamed `allow_declassified_for_destructive`** (covers both, default false). The old name is
     still accepted by `SecurityPolicy` (an alias plus a read-only property), by `agentos.config.yaml`, and as
     `AGENTOS_ALLOW_EXTRACTION_FOR_DESTRUCTIVE`; the new name wins.
4. **Migration.** No flow in `examples/`, `demo/` or the test fixtures uses a validator; only three test files
   do.
   - `test_acceptance.py`: `bounded_number` now has `min`/`max` and an integer input; a float string is now
     rejected, by design.
   - `test_static_analyzer.py` and `test_static_bypasses.py`: unchanged; they pass with the stricter rules.
   - The use case 06 README no longer recommends `http_allowlist` for a validator.
5. **UI.** The validator drawer uses the same `FieldEditor` as extraction: the five types, enum chips, the
   pattern dropdown and admin allowlist names. Legacy names show as their new type. The node card shows
   "declassifies", and the run panel shows "trusted · declassified by validator (<node>)".
   `/api/v2/node-specs` adds `declassifies` and `allowlist_names` to the validator entry too.

### Tests (all MOCK)
`agentos/tests/flows/test_validator_2_5b.py` has 62 tests:
- **The exact bypass and its variants** (enum without values, bounded_number without or with only one bound,
  `free_text`, `text`, `http_allowlist`, an unconfigured allowlist): refused at publish with the validator
  message, and the `to` sink is still refused. A direct runtime call fails closed (`invalid_config`, the
  attacker address isn't echoed).
- **A pre-2.5b flow fails closed at run time** with a `validator_rejected` event, no `declassified` event and
  no email.
- **Accepted values are canonical** (enum trimmed; bool real or exact strings; int; legacy int; pattern;
  allowlist and legacy allowlist canonical).
- **Near-misses are rejected:**
  - enum: case, prefix, newline payload, "category: legit", attacker address, int, list;
  - bool: "True", "yes", "1", " true", 1, 0, None;
  - int: True, "3", 3.0, out of range both ends, legacy 42.5;
  - pattern: partial match, lowercase;
  - allowlist: attacker address, look-alike suffix, nested object.
- **Bad constraints are refused:** one enum value, bad charset, min > max, |max| > 10^9, a stray key, a pattern
  without its name, allowlist_match without a name.
- **Labels:** SECRET in gives SECRET out, directly and through a flow, with the marker. Labels are identical at
  publish and run time, over one and two levels.
- **Recipients:** an enum validator recipient is refused at publish and at run time; an allowlist recipient
  sends the canonical entry, and the attacker address fails.
- **DESTRUCTIVE:** a destructive step gated only by a validator predicate is refused at publish and at run time,
  and allowed with an upstream approval or the admin flag. A destructive argument from a validator is refused
  at publish and at run time.
- **Elsewhere:**
  - `test_extraction_policy_config.py` gains a renamed-flag precedence test.
  - `test_extraction_2_5b.py` asserts the new message and the old flag name.
  - `ui/e2e/builder-2.5b.spec.ts` gains 2 tests: the validator form uses the same builder and shows legacy
    names as the new type; a validator run shows "declassified by validator"; the bypass flow's publish is
    refused with the validator message.
