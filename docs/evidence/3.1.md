Branch `feature/agentos-2.0-phase3.1-audit`, cut from `2.0` at `4523f7b` (2.5b merged). All results are
**MOCK** unless labelled LIVE.

## Design decisions (written before the implementation)

### Part 0: the approval race (CI run 44483492284, job ui-e2e)
**Cause, confirmed in the code.**
1. The worker's engine appends `node_waiting` and `run_waiting` and sets the run status to `waiting` while
   its queue job is still `leased`.
2. The worker calls `queue.release_for_waiting` only after the engine returns.
3. `node_waiting` is the event that makes the run visible as waiting, both in `FlowRunState` and in the UI's
   `pendingApproval`.
4. The approve endpoint builds an engine with no lease. The event store's fencing checker
   (`queue.validate_lease`) allows unleased writes only when the job is `waiting` or `queued`, so an approval
   in this window raises `FencingTokenError`. The route handles only `ValueError`, so the request fails with a
   500 and the decision is lost.

**Fix: the approval path takes over correctly.** The prompt offered two options. Releasing the lease *before*
the waiting event becomes visible opens a crash window: if the worker dies between releasing and writing
`node_waiting`, a persistent (Redis) job is left `waiting` with no visible approval, so the run is stuck
forever. That's the less safe option, so I'm not using it. Instead:
- **Short wait.** The waiting events stay under the worker's lease, as today. The approve endpoint first
  checks the queue job. If the job is still `leased` (being parked), it waits briefly: up to 3 s, in 50 ms
  steps, inside the request (a bounded wait, not a watcher).
- **409 if still parking.** If the job is still leased after the wait, the endpoint returns **409** with
  `{"detail": "Run <id> is still being parked by the worker; retry the decision in a moment", "retry": true}`.
  A `FencingTokenError` raised during the decision also maps to 409. Fencing is checked before any append, so
  no partial decision is written.
- **Exactly once.** A per-run `asyncio.Lock` in the API process wraps the idempotency check (an existing
  `approval_decision` for `run_id + node_id`) and the append. The same decision again returns the same result;
  a different decision returns 400.
- **The UI retries 409.** `decideApproval` retries up to 5 times with a 400 ms pause, then shows the message.

**Test.** The worker's `release_for_waiting` is wrapped so it blocks on an event (the injected delay), and an
approval is sent while the run is visibly waiting and the job is still leased.
- Released within the wait: 200, the run succeeds, exactly one `approval_decision`.
- Not released in time: 409 with no decision written; the retry after release succeeds.
- Two concurrent approvals: one decision.

This runs against the file store and the Mongo store; the Mongo variant is LIVE and runs in the mongo-live
job when Mongo is available. Then the Playwright test runs with `--repeat-each=20`.

**Remaining gap:** the per-run lock is per API process. Platform mode with several API processes could, in
theory, append two identical decisions concurrently. That's noted in Gaps.

### Part 0b: agent tool picker and `calculator`
- **Endpoint.** `GET /api/v2/agents/tool-options` lists what the server's `ToolCatalog` resolves for agents:
  the built-in agent tools (`fetch_url`, `send_email`, `calculator`) plus approved MCP tools of enabled
  servers. It uses the same catalog the save path checks. The hard-coded list in `Agents.tsx` is removed.
- **`calculator`.**
  - NodeSpec, side effect `none`, input `{expression: string}`, output `{result}`.
  - The evaluator is a whitelist over the Python AST: numbers, `+ - * / ** % //`, unary `+ -`, parentheses,
    and calls only to `abs, round, min, max, sqrt, floor, ceil, log, exp`.
  - Refused: any name other than those functions, attribute access, subscripts, comprehensions and strings.
  - Limits, from `agentos/flows/expressions.py` where it has them: source length ≤ the expression cap, AST
    node count capped, exponents capped (|exponent| ≤ 64 and |base| ≤ 10^6 when the exponent is above 4),
    |result| ≤ 10^15, and no NaN or infinity.
  - The output is untrusted, like every tool output (`tool_output_label`).
  - It's available through the agent proxy, and also as a flow node (engine branch + contract test), because
    the palette lists every NodeSpec.
- **`file_read` / `file_write` aren't added.** They need the 3.5 sandbox and path confinement: planned for 3.5.

### Part 1: audit log
**Data model** (`agentos/audit/models.py`):
```
AuditEntry {seq:int>=1 gapless, ts:str (server UTC ISO-8601), actor:str ("local-admin" | "system"),
            source: ui|api|cli|system|webhook|scheduler, action:str (dotted, ^[a-z0-9_]+(\.[a-z0-9_]+)+$),
            target:{type:str, id:str}, outcome: ok|refused|failed, details:{...metadata only},
            prev_hash:str (64 hex), hash:str (64 hex)}
```
- **What `details` may hold:** names, ids, versions, hashes, sizes, counts, rule names and reasons written by
  AgentOS.
- **Enforced by construction and by a sanitizer.** Values may only be str, int, bool, None, or lists or dicts
  of those, at most 2 levels deep. Strings are capped at 300 characters and lists at 50 items. A string
  matching the canary-secret patterns, or one that looks like key material (long base64 or hex blocks of 40+
  characters, unless the key name ends in `sha256`, `hash` or `fingerprint`), raises.
- **Call sites pass only metadata.** No payload, body, prompt or secret value is ever handed to the audit
  writer. A test scans every entry written by the test suite for canaries, the API token and the untrusted
  test payloads.

**Chain and key scheme.**
- `hash = HMAC-SHA256(K, canonical_json(entry without "hash"))`. The canonical JSON has sorted keys, no
  whitespace (`separators=(",", ":")`), `ensure_ascii=False`, UTF-8, and includes `prev_hash`.
- `prev_hash` of seq 1 is 64 zeros. Each later `prev_hash` is the previous entry's `hash`.
- `K = HKDF-SHA256(ikm = master key, salt = b"agentos-audit", info = b"agentos-audit-v1", length 32)`. It's
  derived in memory when the server or CLI starts and is never stored, logged or returned. Its `key_id` (a
  sha256 prefix) isn't recorded either.
- **Verification** walks the chain, checking for each entry the seq (contiguous from 1), `prev_hash`, the
  recomputed HMAC and the schema. It reports `{status: ok|broken|empty, entries_checked, first_broken_seq,
  reason}`. This detects edited, deleted, inserted and reordered entries, and the wrong key (seq 1 fails).
- **Truncation: the head checkpoint.**
  - It holds `{seq, hash, mac}`, where `mac = HMAC(K, "head|<seq>|<hash>")`, written atomically after every
    append: in file mode with the crash-safe `atomic_write_text` (flush + fsync + rename); in Mongo as a
    `audit_head` document updated only from the expected previous seq.
  - Verification requires a valid head MAC, and the entry at `head.seq` must have `head.hash`.
  - Entries *after* the head are accepted if they chain correctly (a crash between the append and the head
    write). Entries missing *below* the head means truncation, reported as broken at the first missing seq.
- **Unsound part of the prompt, written down here:** a head checkpoint stored next to the log can't stop an
  attacker with write access who kept an *older genuine* head file from rolling back to it. HMAC prevents
  forging new heads, not replaying old ones. Preventing that needs an external anchor (copying the head hash
  to another system), which is planned and listed in Gaps.

**Storage.**
- **File (Standalone).** `<project>/.agentos/audit/audit.jsonl`, append-only, plus `head.json`. There's one
  writer: an `asyncio.Lock` per store. Standalone is a single process; a second process would need a file
  lock, noted in Gaps.
  - Each append writes one line, then calls `flush()` and `os.fsync()`, then writes the head.
  - The last entry is cached under the lock.
  - **Crash mid-append:** a trailing line without a newline, or that isn't valid JSON, is an unacknowledged
    write (the action wasn't applied, because writing comes first). The reader ignores it, and the next
    append cuts it off before writing. Verification reports `ok` with `partial_tail_ignored: true`.
- **Mongo (Platform).** The `audit` collection has a unique index on `seq` and a unique index on `prev_hash`,
  so two entries can't share a predecessor (no forks).
  - **Append:** read the last entry (highest seq), compute the entry, then `insert_one`. On `DuplicateKeyError`
    (a seq or `prev_hash` conflict), re-read the head and retry, up to 20 times.
  - Then the `audit_head` update.
  - These tests are LIVE and run in the mongo-live CI job.

**Audit-before-apply (fail closed).**
- Every audited admin or security action validates first (no side effects), then writes its audit entry with
  the decided outcome, then applies.
- If the write fails (`AuditUnavailable`), the action isn't applied and the API returns **503**:
  `"Audit log unavailable: the action was not applied"`.
- If applying fails after a successful write, a second entry with `outcome: failed` is attempted.
- A refusal (for example a publish refused by the analyzer) is written as `outcome: refused` with the violated
  rule names. If that write fails, the response is also 503.
- Run-time hot paths (node execution) aren't audited per step; they stay in run events.

| Webhooks | `webhook.create`, `webhook.update`, `webhook.rotate`, `webhook.delete` (ids and names only; never the secret path or key) |

- **MCP events.** The manager's events now go to the audit log instead of the `mcp-server-<name>` pseudo-run
  event stream. Events already stored under `mcp-server-*` stay readable through the existing events API;
  nothing is migrated or deleted.
- **Auth failures.** These are counted in memory per `(source, minute)`. When the first failure of a new
  minute arrives, the previous closed minute is written as one `auth.failure` entry with
  `details {count, window_start}`; the open minute is flushed at shutdown. That's at most one entry per minute
  per source, with no timer or watcher. Auth failures don't fail closed: the request is already refused.
- **Not in this milestone:**
  - **Run cancel:** no cancel endpoint exists yet. It'll be audited when it's added.
  - **MCP server "update":** there's no update route (servers are deleted and re-created).
  - **Both are listed in Gaps.**

**Actor and source.**
- **Actor:** `local-admin` for the local API token; `system` for startup, shutdown, config and MCP lifecycle
  events.
- **Source:** `ui` when the request carries `X-AgentOS-Client: ui`, which the UI's API client sends; `api`
  otherwise. `cli`, `system`, `webhook` and `scheduler` are set by those callers.
- **Ready for 3.4:** the actor is a parameter of `AuditLog.record`.

**API** (same auth as the other `/api` routes):
- `GET /api/v2/audit`:
  - filters `action` (prefix), `actor`, `target_type`, `target_id`, `outcome`, `since`, `until`;
  - newest first;
  - cursor = `before_seq`;
  - `limit` ≤ 200.
- `GET /api/v2/audit/verify`.
- `GET /api/v2/audit/export`: JSONL, as stored.
- CLI: `agentos audit verify` and `agentos audit export [--out file]`. They load the master key the same way
  the server does and read the configured store.

**UI.**
- Govern > Audit log: a table (time, actor, action, target, outcome), filters, a detail drawer (details as
  plain text, never HTML), the chain badge ("Verified · N entries", or "Broken at #k" in red) and export.
- Overview footer: "Audit chain verified" (or broken) from the verify endpoint.

## Implemented: deviations from the design above (each one is the more exact or the safer option)
1. **Provider keys.** The v1 `/api/providers/keys` routes write the project `.env`, not the vault, so they're
   audited as `provider.key.set` / `provider.key.delete`. Details are booleans saying which settings were set,
   never values. The v2 vault routes are `vault.secret.set` / `vault.secret.delete`.
2. **MCP "update" exists.** `POST /api/v2/mcp-servers` upserts, so it's audited as `mcp.server.update` when the
   server already exists, with `target_changed`.
   - **Manager events** map to `mcp.server.started|stopped|start_failed|request_refused|discovered|url_blocked`,
     `mcp.tool.changed` and `mcp.tool.name_rejected`, through `audit_support.mcp_event_to_audit`.
   - **No server-supplied text is kept.** A rejected tool name is recorded only as its sha256. A refused
     method is kept only if it's a plain identifier; otherwise it's recorded as `other`.
3. **The Mongo audit store lives in `agentos/storage/mongo/audit.py`.** The repo rule is that only the Mongo
   adapter imports pymongo. It's imported lazily in Platform mode, so Standalone installs without pymongo still
   work. `ensure_indexes` creates the unique `prev_hash` index.
4. **The 409 body** is `{"detail": {"detail": "...retry...", "retry": true}}`. The UI's `apiErrorMessage` shows
   the inner message.
5. **Calculator limits:** magnitude ≤ 10^18 during evaluation (`expressions.MAX_NUMBER`) and |result| ≤ 10^15.
6. **`builder-run-inspect.spec.ts` "inline approval"** now uses a fresh flow id and skips the screenshot per
   `--repeat-each` repetition. Without that, every repeat after the first failed on "draft already exists",
   before reaching the approval.

## Gaps and known limits
- **Mongo not run locally.** Docker Desktop wasn't running, so every Mongo variant (race, audit store) is
  untested here. They run in the mongo-live CI job, and `AGENTOS_REQUIRE_LIVE_MONGO=1` makes them fail
  rather than skip there.
- **Approval lock is per API process.** In Platform mode with several API processes, two identical decisions
  could in theory both be appended. A storage-level unique decision key would close this; it isn't done.
- **Rollback to an older head isn't detected.** An attacker with write access who kept an *older genuine* head
  file can roll back to it (a HMAC can't stop replay). This needs an external anchor, which is planned.
- **File audit store, Standalone:** one writer process (an in-process lock, no file lock).
- **Auth failures:** the open minute is written at the next failure in a later minute or at shutdown, so a
  crash loses at most one minute's count.
- **Startup entries are best effort.** The server starts even if the audit store isn't writable; every
  audited admin action then fails closed with 503.
- **Not audited yet:**
  - **Run cancel:** no endpoint exists.
  - **v1 routes** other than provider keys: v1 agents, tools, crews, missions, governance policies and
    packaging aren't audited.
- **The server still resolves any NodeSpec name as an agent tool,** for example `condition`. The picker offers
  only `calculator`, `fetch_url`, `send_email` and approved MCP tools; tightening the server is a follow-up.
  `fetch_url` used as an agent tool still returns simulated content in the proxy, as before 3.1.
- **`file_read` / `file_write`** aren't added; they're planned for 3.5 (sandbox and path confinement).
- **README screenshots** were taken before 3.1 and don't show the new Govern → Audit log entry. The builder
  run regenerates them; I restored the committed versions.
- **Test order.** One run with a non-canonical file order (server tests first) showed a `VaultKeyMismatch`
  setup error in `test_flow_api_and_approval_2_1.py`. In the canonical order, and on its own, it passes. I
  didn't investigate it.
