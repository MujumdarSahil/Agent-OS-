# Evidence report: 4.0 natural-language flow builder ("Describe it")

Branch: `feature/agentos-2.0-phase4.0-nl-builder` (off `2.0` @ 3c69311). Status: implemented as designed (owner
approved D1-D13 before implementation); awaiting owner review. All results below are **MOCK** (scripted builder
model) unless stated; nothing here was run against a real provider.

## Design decisions

Principle: the model is never trusted for safety. Whatever it produces is a DRAFT that must pass the same
`FlowDefinition` validation and `StaticFlowAnalyzer.verify()` (same policy, same tool catalog) as the Publish gate.
The builder never publishes and never saves on its own.

**D1. Package split (ports and adapters).** Domain package `agentos/builder/` with no FastAPI or Mongo imports:
`schema.py` (strict flow JSON schema for model output, limits), `prompt.py` (prompt from trusted material only),
`guards.py` (literal provenance check, secret check), `repair.py` (deterministic one-click fixes), `explain.py`
(deterministic explanation and security summary), `diff.py` (flow diff), `service.py` (generate -> validate ->
check -> repair rounds -> report), `mock_builder.py` (scripted MOCK model). HTTP layer:
`agentos_server/routes_v2/builder.py`.

**D2. Endpoints** (capability `build` = builder and admin roles; added to `agentos_server/permissions_table.py`):
- `POST /api/v2/flows/generate`, body `{description (max 4000 chars), answers?: [{question, answer}] (max 3, each max
  500), flow_id?: existing flow, change_request?: (max 1000), base_flow?: the editor's current unsaved graph}`.
  Response `{status: "questions" | "draft" | "error", questions?, flow?, explanation, check: {status: "passed" |
  "fixed" | "failing", violations, fixed: [...], fixes: [...]}, diff? (edit mode), usage: {model_calls, run_id}}`.
- `POST /api/v2/flows/check`, body `{flow}`: the same check and one-click-fix computation, without saving. Used after
  a one-click fix is applied, and by the "Edit with AI" panel.
- Both are POST-only paths, so they do not shadow `GET/PUT /api/v2/flows/{flow_id}`.

**D3. One model call through the AgentOS router.** `AgentOSRouterLLM` without tools (the model gets no tools), with a
`RunGuard` for the pseudo flow id `"builder"`, so run limits and budgets apply (including `flow_daily["builder"]`).
Fallback and cooldowns behave as usual. Cost is computed the same way as engine `llm_call` records. Each generate
request is one pseudo run: `RunRecord(run_id="builder_<hex>", flow_id="builder", mission_name="builder",
trigger="builder")` holding the `llm_call` events, with ledger rows under `"builder"`. This means
`agentos usage rebuild`, Usage and Overview all count builder spend. Model calls per request: 1 generate, at most 1
retry for invalid output, and at most 2 repair rounds, so at most 4, all under the run limit. Known gap: a user flow
literally named `builder` shares this usage bucket. The id is documented, not reserved.

**D4. Prompt from trusted material only.** The system message holds the node specs catalog (type, side effect, config
schema, inputs/outputs, sink rules), the approved agent tools (`ToolCatalog.agent_tool_options()`), allowlist NAMES,
configured Slack channel NAMES, a compact flow JSON schema and the output contract. The user's description, answers
and change request go in a delimited data block (`<<<USER_DATA ... USER_DATA>>>`) that is labelled as data, not
instructions. In edit mode the existing flow JSON (the author's own draft) is included.

**D5. Strict output.** The model returns JSON only: `{"questions": [...]}` (max 3) or `{"flow": {...},
"explanation": "..."}`. Checks, in order:
1. JSON parse.
2. jsonschema, with `additionalProperties: false` on the flow, nodes and edges, node `type` limited to the node types
   that can be flow steps, and at most 30 nodes.
3. Agent tools must be in the approved list.
4. `FlowDefinition(...)`.

Invalid output gets ONE retry. The feedback for that retry is AgentOS's own error message (for example
"node 'x': unknown node type 'foo'"), never the model's text. If the retry is also invalid, the result is
`status: "error"` with a clear message. Raw model output is never stored or logged. Only its length and sha256 are
kept, as in 2.5b extraction.

**D6. No invented recipients or targets.** After validation, every literal email address, URL or host, Slack channel
and allowlist name anywhere in the flow must meet one of two conditions:
- It appears verbatim (case-insensitive) in the description, answers or change request.
- It is an existing allowlist name, a configured Slack channel, or an `http_allowlist` entry.

This covers `pinned_args`, the config url/query/headers/body, and the validator `allowlist_name`. Any other value is
removed and turned into a question (for example "Who should receive the email sent by 'notify'?"), returned as
`status: "questions"` (max 3). Values the user stated are placed as `pinned_args`.

**D7. No secrets.** `looks_like_secret()` reuses three existing patterns:
- the audit-chain patterns (`agentos/audit/chain.py` `_SECRET_PATTERNS`),
- the router's prefixed-key pattern (`agentos/llm/router_llm.py` `_KEYLIKE`),
- the 3.4 API token prefix `aos_pat_`.

It is applied in two places:
- (a) The input description, answers and change request. A match is refused with 400 before any model call, so a
  pasted key never reaches a provider.
- (b) The model output. A match is treated as invalid output, and the retry message never echoes the value.

Flows reference secrets only by vault name (`{"vault": "<name>"}` headers), which is allowed.

**D8. Check and repair.** The analyzer runs with the server's policy and the MCP tool catalog, exactly as publish
does. If there are violations, there are up to 2 repair rounds. In each round the model gets the draft plus the
violations as AgentOS wrote them (rule, node, argument, path, reason). The fixed draft goes through D5 to D7 again and
is re-checked. What changed between rounds is reported as `fixed` entries (what and why).

Each violation still left gets deterministic one-click fixes. The server applies and re-checks each fix in advance
(`fix.flow`, `fix.passes`). The fixes are:
- **Recipient arg** (`to`, `channel`, http `url`) that is unpinned or untrusted:
  - "Pin this recipient to <value>", once for each matching value from the description. The value must be an email
    for `to`, a configured channel for `channel`, or a URL for `url`.
  - "Use allowlist <name>", once for each existing allowlist. This inserts a `validator` with `allowlist_match`.
- **Untrusted body, text, query or headers going to an external sink**: "Add an approval before <sink>". This inserts
  an `approval` node that approves those args and rewires the mapping through it.
- **Recipients are never fixed by an approval.** A recipient taken from incoming data only gets pin or allowlist
  fixes. If neither is possible, the result says "refused: a recipient taken from the incoming message is not
  allowed; name a fixed recipient or an admin allowlist".

Status: `passed` = clean the first time. `fixed` = clean after repair rounds. `failing` = violations remain, shown
with their one-click fixes.

**D9. Explanation.**
- The step-by-step text is generated deterministically from the flow in topological order, using per-node-type
  templates.
- The model's short `explanation` is shown separately as escaped plain text, labelled "Model summary".
- The security summary is fully deterministic, built from the analyzer labels. It lists:
  - which inputs are UNTRUSTED,
  - which sinks they reach,
  - the pinned values,
  - the approval steps,
  - the external-send sinks and their recipients.

**D10. Saving and audit.** The builder never saves or publishes. In the UI, "Create draft" calls the normal
`POST /api/v2/flows` (audited as `flow.save`) with a flow id the user confirms, then opens the visual editor, where the
normal Publish check applies. The generate endpoint audits `flow.generate` before the model call (the 3.1 rule) with
metadata only: `description_chars`, `description_sha256`, `mode` (new/edit) and `answers` (a count). The outcome is
audited the same way: `status`, `model_calls`, `repair_rounds`, `violations` (a count). The description text is never
audited.

**D11. Edit with AI.** The editor gets a side panel. A change request is sent to generate in edit mode, using the
editor's current graph. The server returns the proposed flow, a `diff` (added, removed and changed nodes and edges)
and the check report. "Apply" loads the proposal into the editor as unsaved changes; undo works, and normal Save and
Publish apply. "Discard" drops it.

**D12. MOCK mode.**
- `agentos/llm/mock_model.complete()` recognises the builder's system marker and hands the call to
  `agentos/builder/mock_builder.py`.
- That module returns deterministic JSON chosen by phrases in the data block. It covers:
  - the 3 UI examples,
  - the 12 eval cases,
  - test fixtures: unknown node type, extra field, more than 30 nodes, secret in the output, a draft that repair can
    fix, a draft that can never be fixed, and prompt injection.
- MOCK calls still go through the router, so they produce `llm_call` events, are subject to run limits, and cost $0.
- MOCK eval tests the guard rails, not model quality; `4.0-eval.md` says so.
- `scripts/nl_builder_live_eval.py` (not in CI) runs the same 12 cases against the real router and prints only
  metadata and the success rate.

**D13. UI.**
- **Flows page:** "+ New flow" offers two cards. "Build visually" holds the existing id/name form with the same test
  ids. "Describe it" opens `/flows/describe`.
- **Describe page:**
  - a text box with 3 example chips;
  - a preview with a read-only canvas (reusing `toCanvas`, `autoLayout` and `nodeTypes`), coloured by label:
    UNTRUSTED red, trusted green, external sinks marked;
  - the explanation;
  - questions answered inline, then "Continue";
  - the check result with fix buttons;
  - buttons "Create draft", "Refine" and "Start over".
- **Editor:** an "Edit with AI" toolbar button opens a side panel that shows the diff.

## (d) Known gaps and anything skipped

- **LIVE eval not run** (needs provider keys; this session does not use the owner's keys or the real home). MOCK
  proves the guard rails, not the generation quality of a real model.
- **Builder pseudo runs are visible.** Each generate request is a run with `flow_id="builder"` and
  `trigger="builder"`, so it shows in Runs and counts in the Overview run KPIs. A user flow literally named
  `builder` shares the usage bucket and budget (documented, not reserved).
- **Approval fixes cover a limited set of args:** only send_email `body`/`subject` and send_slack `text`. There is
  no approval fix for http_request body/query/headers (the host-allowlist rule does not accept approvals), and none
  for agent-tool arguments (an approval cannot declassify agent context). Those get pin/allowlist fixes only, or
  none.
- **"Use allowlist" fix scope:** it is offered only when the recipient is mapped from data (it inserts a validator
  on that mapping), and only for `to`/`channel`.
- **Invented-target detection** is pattern-based (emails, `http(s)://` URLs, bare url values, Slack channel and
  allowlist names), with EXACT matching against what the user stated (see "Review fix"). An email or URL inside free
  text, such as an agent goal, also becomes a question, so a few false positives are possible. A value stated in a
  different form (for example a URL with a trailing slash, or a different path) is treated as invented. A bare host
  the user wrote ("api.example.com") allows any URL on exactly that host (any scheme, port and path); the query
  string is not compared.
- **Secret detection** reuses the existing patterns, so false positives are possible: text like `password: x`, or
  any run of 32 or more letters and digits, is refused.
- **Edit with AI questions** are shown, but are answered by rephrasing the change request; there is no inline answer
  box in the panel. The Describe page has inline answers.
- **No loops:** generated flows never contain loops; bounded loops are built in the visual editor.
- **Model summary** is shown as escaped plain text labelled "unverified". The step list and the security summary
  are deterministic.
- **Mongo:** the builder uses only storage interfaces; it has no LIVE Mongo test of its own.

## Review fix: exact target matching (after the owner's review)

**Finding (reviewer):** `invented_targets()` matched by substring (`email not in src`, `url.lower() in source`).
- A description stating `bob.smith@corp.local` let a draft pin `smith@corp.local`.
- A description stating `https://api.example.com.evil.net/x` let a draft pin `https://api.example.com`.

**Fix** (`agentos/builder/guards.py`): `StatedTargets.from_text()` extracts the exact set of emails, URLs, bare hosts
and words from the stated text, using the same regexes, and every check is now exact set membership.
- **Emails:** compared lower-cased, with trailing punctuation removed.
- **URLs:** compared by (scheme, host, port, path).
  - Scheme and host are lower-cased, default ports 80/443 are dropped, and an empty path counts as `/`.
  - A URL with user info (`user@host`) never matches.
- **Bare hosts:** a host the user wrote matches a URL only when the URL has exactly that host. A host found inside an
  email or URL does not count as a bare host.
- **Slack channels:** compared as exact words, both in the guard and in the "Pin this recipient" channel candidates
  (`repair.py`), which had the same substring flaw.

**Tests:** 28 added to `agentos/tests/test_nl_builder_4_0.py`.
- **Emails:** suffix address, prefix address (`bob.smith@corp.local.evil.net`), a different user on the same domain,
  a stated address that is a prefix of the pin, trailing punctuation, case differences (allowed).
- **URLs:** host that is a prefix or suffix of the stated host, longer path, different scheme or port, user info,
  trailing punctuation, scheme and host case, default port, empty path.
- **Bare hosts:** exact host only, a host inside an email does not count.
- **Slack channels:** exact word match.
- **End to end:** the model pins `call@corp.local` where `oncall@corp.local` was stated -> question.
